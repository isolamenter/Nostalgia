《归档故乡》游戏技术方案文档（Web架构）

一、项目技术定位

《归档故乡》不是以高强度操作、战斗或3D沉浸为核心的游戏，而是一款以叙事探索、档案交互和现实偏移体验为核心的 Web 游戏。

技术方案围绕作品世界观设计：档案、数据库、交通路线、登记系统、生活记录等普通流程共同构成现实。游戏技术应服务于“记录如何塑造现实”这一主题。

二、总体技术路线

最终采用：Phaser 3 \+ React \+ TypeScript 混合架构。

核心原则：

1\. 空间世界使用游戏引擎实现。  
2\. 档案、系统、界面等记录空间使用 Web 前端实现。  
3\. 两套系统共享统一世界状态。  
4\. 优先保证叙事表达和开发效率，而非追求3D表现。

三、技术架构

浏览器客户端

├── Phaser 3 游戏层  
│   ├── 县城地图  
│   ├── 人物移动  
│   ├── 场景交互  
│   ├── 物件检查  
│   └── 环境音效  
│  
├── React 应用层  
│   ├── 档案系统  
│   ├── 手机界面  
│   ├── 数据库查询  
│   ├── 表格与登记页面  
│   └── 剧情文本展示

    ├── 世界状态  
    ├── 事件系统  
    ├── 角色关系  
    └── 存档数据

四、核心技术选型

1\. Phaser 3

用途：负责现实空间表现。

适用内容：  
\- 安置区街道  
\- 旧城区域  
\- 公交线路  
\- 修鞋铺  
\- 气象站  
\- 档案室等探索空间

选择原因：  
Phaser 3 专注 Web 2D 游戏开发，能够提供地图、输入、碰撞、动画和事件系统，同时保持较低开发成本。

2\. React

用途：负责记录空间。

适用内容：  
\- 户籍系统  
\- 档案查询  
\- 手机消息  
\- 数据库界面  
\- 关系网络

选择原因：  
《归档故乡》的异常大量发生在“系统如何记录人”的层面，React 更适合构建复杂交互界面。

3\. TypeScript

用途：统一类型系统。

负责：  
\- 事件定义  
\- 世界状态管理  
\- 剧情节点  
\- 数据结构约束

五、游戏运行逻辑

游戏由统一世界状态驱动：

玩家探索现实空间 → 触发事件 → 修改记录状态 → 系统界面变化 → 现实产生新的解释。

例如：

玩家发现一个没有明确归属的维修记录。

系统生成补全信息。

多个局部解释进入数据库。

数据库反过来影响居民身份和空间状态。

六、数据设计

核心数据对象：

WorldState  
世界当前状态。

Character  
人物身份、关系和记录。

ArchiveEntry  
档案条目。

Location  
地点与空间状态。

Event  
触发事件。

Relation  
人物之间的社会关系。

七、第一阶段开发目标

不制作大型开放世界。

第一版本采用：

固定场景探索 \+ 档案交互 \+ 剧情事件。

以《第二份》作为技术验证章节。

功能范围：

\- 一个安置区场景  
\- 数个可交互物件  
\- 一套档案系统  
\- 一个完整异常循环  
\- 基础存档

八、为什么不采用Unity

Unity 的优势主要集中于3D场景、物理模拟、大规模动画系统。

但《归档故乡》的核心体验来自：

\- 文件  
\- 记录  
\- 分类  
\- 关系  
\- 日常流程

使用 Unity 会增加工程复杂度，却不会明显增强核心体验。

Web 架构能够让“网页、系统、档案”本身成为叙事媒介。

九、后续扩展方向

未来可以增加：

\- PWA离线运行  
\- 云端存档  
\- 多章节动态加载  
\- 更复杂的数据模拟  
\- 移动端适配

十、结论

《归档故乡》采用 Web 游戏架构不是技术妥协，而是媒介选择。

Phaser 负责故乡的空间，React负责故乡的记录。

二者共同构成一个会被保存、修改和重新解释的世界。
